Auditoría técnica de código fuente
Fecha de revisión: 10 de septiembre de 2026

ALCANCE Y MÉTODO
================
Este documento describe el estado observado del repositorio /home/jimmy/tinkus.
La revisión fue estática y no modificó reglas de negocio, datos ni configuración de producción.
Se inspeccionaron código fuente, manifiestos, rutas, modelos, pruebas y archivos de despliegue.
No se leyeron ni se reproducen contraseñas, tokens, cadenas de conexión ni valores de archivos .env.
Los respaldos, documentos personales, binarios, node_modules, dist y estados locales de herramientas
se contabilizan como artefactos, pero no se consideran código fuente activo.

1. RESUMEN DEL PROYECTO
=======================
Sistema web monorepo para administrar la fraternidad Tinkus Puros y Naturales. Cubre cuentas,
roles, gestiones, prerregistros, fraternos, postulantes a guía, guías, bloques administrativos,
cuotas y comprobantes, QR, asistencias, tallas e indumentaria, anuncios, reportes, formación,
tokens de registro, traspasos, auditoría y respaldos.

Aplicaciones:
- backend/: API REST Node.js/Express/TypeScript con MongoDB mediante Mongoose.
- frontend/: SPA React/TypeScript/Vite.
- r2-worker/: Worker Cloudflare para almacenamiento privado en R2.

Métricas del código auditado:
- 131 archivos TypeScript en backend/src.
- 121 archivos TypeScript/TSX en frontend/src.
- 1 archivo TypeScript en r2-worker/src.
- 41.935 líneas aproximadas en los tres árboles fuente.
- 27 modelos MongoDB.
- 22 archivos de rutas, de los cuales 21 se montan en server.ts.
- 26 controladores, 17 servicios y 12 middlewares de backend.
- 50 vistas, 22 componentes, 19 módulos API y 10 archivos de tipos del frontend.
- 148 operaciones HTTP detectadas en routers; 141 pertenecen a routers montados y 7 a loginRoutes heredado.
- 11 archivos de pruebas backend; 11/11 pasaron durante esta auditoría.

Estado general: el sistema tiene cobertura funcional amplia y reglas defensivas importantes, pero
mantiene deuda por archivos monolíticos, duplicación histórica, tipos flexibles y controles de acceso
repartidos entre frontend y backend. El backend compila; el chequeo TypeScript estricto del frontend
no pasa actualmente y sus errores se detallan en Riesgos detectados.

4. ARQUITECTURA GENERAL
=======================
Patrón principal: ruta -> middleware -> controlador -> servicio/modelo -> MongoDB/R2.
El frontend consume JSON y multipart con Axios; React Query mantiene caché y refrescos.
PerfilUsuario es la identidad central. Rol y Gestion se referencian desde el perfil. La participación
se agrega mediante Preregistro y, si corresponde, Fraterno. Cuotas, tallas, guía y bloque se relacionan
con ese núcleo sin duplicar la identidad.

El backend sirve /uploads primero mediante R2 y luego por almacenamiento local como fallback. En modo
local de producción puede servir frontend/dist. En nube, frontend y backend se despliegan separados.
Las transacciones Mongo se usan en operaciones críticas y algunos servicios contienen fallback para
instancias Mongo que no soportan transacciones.

7. BASE DE DATOS
================
MongoDB mediante Mongoose. No hay migrador versionado tradicional: las migraciones son scripts TS y
dos de ellas se ejecutan en preDeploy de Railway. Se usa eliminación lógica en múltiples entidades,
con fechaEliminado/usuarioEliminador, pero no de forma uniforme: Bloque puede eliminarse físicamente.

Colecciones explícitas observadas incluyen perfil_usuarios, roles, gestiones, documentos_usuarios,
preregistros, fraternos, cuotas, detalle_cuotas, aceptaciones_terminos_pago, anuncios, notificaciones,
asistencias, pasos_videos, tokens_registro y traspasos. Otros modelos usan pluralización de Mongoose.

Índices críticos:
- PerfilUsuario: CI y email únicos.
- Rol: código único. Gestion: unicidad de año/nombre según esquema.
- Preregistro: número único y usuario+gestión único activo.
- Fraterno: preregistro y número únicos; usuario+gestión único.
- Guia: preregistro, usuario y postulante únicos según condiciones.
- Bloque: nombre+gestión único; guía única y guiasIds únicos si la lista existe.
- DetalleBloque: una asignación activa por fraterno; índice bloque+género.
- Cuota: una por preregistro; DetalleCuota: cuota+número de pago único.
- TallaFraterno: una por fraterno y/o usuario mediante índices parciales.
- AceptacionTerminosPago: usuario+gestión+versión única.

9. AUTENTICACIÓN
================
La ruta activa de login es POST /api/perfilusuario/login; loginRoutes.ts es heredado y no está montado.
El frontend guarda AUTH_TOKEN y AUTH_USER en localStorage. Axios adjunta Authorization: Bearer <token>.
auth.ts verifica JWT_SECRET, carga PerfilUsuario activo con roles poblados y lo asigna a req.usuario.
El endpoint GET /api/perfilusuario/usuario hidrata la sesión para useAuth/React Query.

Controles adicionales: intentosFallidos, bloqueadoHasta, ultimoLogin, requiereCambioPassword y cambio
obligatorio. El modo capacitación agrega cabeceras X-Modo-Capacitacion-*; el backend limita su uso a
administradores y crea una vista impersonada reducida. Cerrar sesión registra auditoría y elimina el
token local. Riesgo: localStorage es accesible ante XSS; CSP y sanitización deben considerarse.

10. ROLES Y PERMISOS
====================
Los roles son documentos configurables y un usuario puede tener múltiples. Códigos especiales
reconocidos: ADMIN/ADMINISTRADOR/SUPERADMIN/SUPERADMINISTRADOR y GUIA.

Catálogo backend: 53 permisos aproximadamente, agrupados en vistas y acciones: usuarios, roles,
gestiones, preregistros, pagos, guías/bloques, asistencias, tallas, indumentaria, fraternos, traspasos,
anuncios, auditoría, formación y tokens. normalizarPermisosRol agrega automáticamente la vista asociada
a una acción. GUIA conserva permisos base compatibles en authorizePermission.

Capas de protección:
- Backend: authenticate, authorizePermission, soloAdministracion, soloAdministradorReal,
  administracionOGuia y soloPropietarioRespaldo.
- Frontend: AppLayout filtra menú por rol/permisos y redirige accesos no visibles.

Hallazgo: permisoPorRuta contiene VISTA_DIRECTORIO_BLOQUES, pero no está en PERMISOS_CATALOGO.
Además, administradores ven casi todas las opciones por código aunque no se evalúe cada permiso.
La autorización decisiva debe seguir estando en backend; ocultar menú no es seguridad.
Respaldo total depende además de un correo propietario codificado en frontend y middleware.

11. MÓDULOS DEL SISTEMA
=======================
Formato: objetivo; acceso; frontend; backend/modelos; dependencias; riesgo.

USUARIOS / GESTIÓN INTEGRAL
Objetivo: alta, consulta, aprobación, edición, documentos, bloqueo y eliminación integral.
Acceso: administración o permisos USUARIOS_*; usuario consulta/edita su perfil según autorización.
Frontend: vistas perfilUsuario, PerfilUsuarioApi, formularios y tipos PerfilUsuario/Documento.
Backend: perfilUsuarioRoutes; PerfilUsuarioController, CompletarPerfil, AutorizacionEdicionPerfil;
PerfilUsuario, DocumentoUsuario, AutorizacionEdicionPerfil; eliminacionUsuarioService.
Dependencias: roles, gestión, preregistro, R2, correo, pagos, guía, tallas y auditoría.
Riesgo: controlador/ruta/API/formularios gigantes y eliminación transversal compleja.

GESTIONES
Objetivo: periodos, cupos, fechas, apertura/cierre y gestión activa.
Acceso: permisos GESTIONES_*.
Frontend: vistas gestion, GestionApi, GestionForm/DetailModal, GestionType.
Backend: GestionRoutes/Controller y Gestion.
Dependencias: casi todos los registros operativos.
Riesgo: controller/routes/type muy grandes; cambiar gestión activa afecta todo el sistema.

PRERREGISTROS Y TOKENS
Objetivo: inscripción previa y alta controlada mediante token/cupo/tarifa.
Acceso: usuario sobre sus registros; administración para revisar/editar/eliminar/tokens.
Frontend: vistas preregistro/tokens, APIs y formularios.
Backend: PreregistroRoutes/Controller, TokenRegistroRoutes/Controller y modelos homónimos.
Dependencias: usuario, gestión, cuota, fraterno, documentos y auditoría.
Riesgo: concurrencia de cupos y consistencia del consumo atómico del token.

FRATERNOS Y TRASPASOS
Objetivo: membresía aprobada, lista de espera y transferencia de cupo.
Acceso: administración y consulta propia.
Frontend: vistas fraterno, FraternoApi y tipos.
Backend: Fraterno/Traspaso routes, controllers, services y modelos.
Dependencias: preregistro, cuota, bloque, tallas y usuario.
Riesgo: no confundir cuenta, preregistro y fraterno; conservar historial al retirar.

GUÍAS, POSTULANTES Y BLOQUES
Objetivo: selección de guías, agrupación administrativa y asignación de integrantes.
Acceso: administración supervisa; guía opera solo su bloque; fraterno ve su bloque/guías.
Frontend: vistas guia y MiBloqueFraterno, BloqueGuiaApi/GuiaApi y tipos.
Backend: GuiaRoutes/Controller, PostulanteGuiaController, servicios de bloque y modelos relacionados.
Dependencias: usuario, rol, gestión, preregistro, fraterno, pagos, tallas, auditoría.
Riesgo: sincronización de guiaId legado con guiasIds y contadores derivados.

PAGOS Y TÉRMINOS
Objetivo: planes dinámicos, pagos, revisión, saldos, QR, plazos y aceptación versionada.
Acceso: usuario registra/consulta; administración revisa/configura.
Frontend: vistas cuota, CuotaApi, ConfiguracionPagoApi/ConfiguracionQrPago.
Backend: Cuota/ConfiguracionPago routes/controllers, PlanPagos/Sincronizacion services y cuatro modelos.
Dependencias: preregistro, gestión, R2, notificación y auditoría.
Riesgo: dinero, idempotencia, revisión y no recalcular fórmulas fuera del servicio vigente.

TALLAS E INDUMENTARIA
Objetivo: tallas por persona, resumen productivo y entrega/devolución de prendas.
Acceso: actualmente administración registra/corrige; usuario consulta sus tallas.
Frontend: IndumentariaView, MisTallasView, IndumentariaApi, constants/tallas.
Backend: IndumentariaRoutes/Controller, servicios de índice/usuarios y tres modelos.
Dependencias: usuario, fraterno, cuotas y QR.
Riesgo: registros históricos por usuario o fraterno, normalización y categorías no válidas.

ASISTENCIAS
Objetivo: entrada/salida propia, administrativa o QR para fraternos/postulantes a guía.
Acceso: usuario/guía y administración según endpoint.
Frontend: vistas de asistencia y APIs correspondientes.
Backend: dos routers/controllers y Asistencia.
Dependencias: identidad QR, gestión, preregistro/fraterno/postulante.

COMUNICACIÓN Y AUDITORÍA

RESPALDOS

13. FLUJOS PRINCIPALES
======================
Registro: token/configuración -> CrearCuenta -> POST registro -> PerfilUsuario/documentos -> posible
consumo transaccional de TokenRegistro -> Preregistro -> Cuota/fraterno según reglas -> login.

Login: credenciales -> bcrypt/JWT -> token local -> GET usuario -> AppLayout/Comunicados según rol ->
cambio obligatorio si aplica.

Inscripción: gestión abierta y cupo -> Preregistro -> revisión/aprobación -> Fraterno con código
secuencial -> cuota sincronizada -> asignación opcional a bloque.

Pago: configuración vigente -> aceptación de términos por versión -> selección dinámica de plan ->
solicitud/visualización de QR -> registro de DetalleCuota -> revisión administrativa -> sincronización
de saldo/estado -> habilitaciones posteriores.

Guía/bloque: usuario/preregistro -> postulante -> evaluación/elección o promoción administrativa ->
Guia/rol -> asignación única a Bloque -> búsqueda de usuario/fraterno -> creación de membresía si
corresponde -> DetalleBloque con validación de cupos.

Tallas: administración localiza usuario/fraterno -> registra TallaFraterno -> resumen por sexo/talla ->
entrega solo cuando la cuota total cumple la condición del backend.

QR/asistencia: usuario genera credencial firmada/versionada -> administrador escanea o busca -> backend
verifica identidad -> presenta ficha -> registra entrada evitando duplicado diario.

14. PAGOS
=========
Cuota representa deuda; DetalleCuota representa movimientos. ConfiguracionPago guarda tarifas, QR y
términos por gestión. PlanPagosService es la autoridad de distribución para 1, 2 o 3 cuotas;
SincronizacionCuotaService recalcula saldo y estado a partir de pagos válidos. No deben duplicarse
fórmulas en vistas, reportes ni bloques.

Estados de cuota: PENDIENTE, PAGO_PARCIAL, PAGADA, VENCIDA, CANCELADA. Revisión de pago: PENDIENTE,
VERIFICADO, OBSERVADO o RECHAZADO. Métodos: EFECTIVO, QR o MIXTO. Los comprobantes se guardan por
ruta y deben resolverse vía backend/R2.

Los términos se aceptan por usuario+gestión+versionTerminos. Cambiar solo el texto sin elevar la
versión conserva aceptaciones; elevarla exige una nueva aceptación. La evidencia guarda el contenido
aceptado, fecha, IP y agente.

15. TALLAS E INDUMENTARIA
=========================
TallaFraterno admite vínculo por fraterno o usuario para cubrir cuentas aún no promovidas. Los índices
parciales evitan duplicados. El backend normaliza/valida mediante IndiceTallaService y los reportes
distinguen talla válida, ausente y valor no reconocido. Un valor no reconocido no debe sumarse como
producción ni corregirse automáticamente sin revisión.

Indumentaria administra polera, chamarra e indumentaria del traje. EntregaIndumentaria conserva estado,
responsables y devolución. La entrega exige cuota PAGADA y saldo cero según controlador.

16. GUÍAS Y BLOQUES
===================
Bloque es administrativo, sin matriz ni posiciones. Límites vigentes: máximo 2 guías hombres, 2 mujeres,
40 integrantes hombres, 80 mujeres, total 120. Un guía activo solo puede pertenecer a un bloque.
DetalleBloque representa pertenencia, no ubicación física.

guiaId es una referencia principal heredada y guiasIds es la lista vigente; ambos deben mantenerse
sincronizados hasta completar una migración de consumidores. Retirar guía del bloque conserva Guia y
rol; quitar rol limpia asociaciones, inactiva Guia, pero conserva identidad, preregistro, fraterno,
pagos y tallas. La asignación crítica usa servicios con transacción, índices únicos y recuperación ante
colisiones. Los contadores del bloque son derivados y deben auditarse contra detalles reales.

17. REPORTES
============
ReporteRoutes ofrece formación, tallas, tallas/primera cuota, almacenamiento y ejecutivo. ReporteService
parte de usuarios cuando el reporte exige todas las cuentas y enlaza opcionalmente fraterno, pagos,
tallas y bloque. Esto evita perder administradores/guías sin perfil fraterno. El frontend muestra
tarjetas desplegables y genera hojas Excel con resúmenes y listados.

Riesgos: consultas y joins manuales en memoria, tablas muy anchas, generación Excel en navegador,
distinción semántica entre SIN REGISTRO/PENDIENTE/NO APLICA y normalización de sexo/talla.

18. QR
======
Hay tres conceptos distintos:
1) QR de credencial personal: token de identidad firmado/versionado.
2) QR de pago: imagen configurada por plan/cuota y QR de saldo.
3) QR de token de registro: código de alta/cupo.

CredencialQrRoutes permite credencial propia, búsqueda, identificación manual y verificación. La cámara
requiere HTTPS; existe alternativa de foto/archivo. credencialQrVersion permite invalidar credenciales
anteriores. El navegador nunca recibe R2_WORKER_TOKEN.

19. AUDITORÍA
=============
auditarActividad se monta antes de routers. AuditoriaService registra acciones específicas con usuario,
módulo, entidad, descripción, antes/después, IP y user-agent. Se registran también logout, cambios de
bloque, formación, pagos y operaciones administrativas. La vista AuditoriaView consulta el módulo.

Debe revisarse periódicamente que no se guarden password, JWT, comprobantes binarios ni información
innecesaria dentro de datosAntes/datosDespues. Auditoría no sustituye backups ni control transaccional.

20. CONEXIÓN FRONTEND-BACKEND
=============================
Axios usa VITE_API_URL como base y agrega Bearer token. En desarrollo Vite proxifica /api y /uploads a
localhost:4001. En nube, VITE_API_URL debe señalar al backend Railway con prefijo /api. CORS usa
FRONTEND_URL/entorno para autorizar el origen Vercel. Las imágenes relativas se resuelven retirando
/api del origen del backend y consultando /uploads/...; backend prueba R2 y fallback local.

Un push solo despliega ambos servicios si Railway y Vercel están vinculados al mismo repositorio/rama
o a repositorios que reciban el mismo commit. Esa asociación pertenece a las cuentas externas y no
puede deducirse únicamente del código; debe verificarse en los paneles de Deployments/Settings.

21. VARIABLES DE ENTORNO

22. DEPLOY
==========
Railway raíz: build con Railpack ejecuta npm run build, que instala/compila backend. PreDeploy ejecuta
migrarArchivosPorCi.js y migrarPermisosYBloquesGuia.js; luego node backend/dist/index.js. Healthcheck:
/health, timeout 120 s y reinicio por fallo. Railpack instala Ghostscript.

Vercel frontend: framework Vite, npm run build, salida dist y rewrite SPA a index.html. Assets tienen
caché inmutable. El proyecto de Vercel debe tener Root Directory=frontend o configuración equivalente.

Cloudflare: Worker tinkus-r2-storage, binding ARCHIVOS al bucket configurado, observabilidad activa.
El código backend actúa como única puerta de acceso a archivos. Operación local: Docker Mongo, HTTPS
y scripts documentados en RED_LOCAL.md.

26. RIESGOS DETECTADOS
======================
CRÍTICOS/ALTOS
- Frontend no pasa tsc estricto: alias @/constants y @/security faltan en paths; InscripcionType no
  existe; hay errores de unión string/rol, readOnly no admitido, Map<unknown,unknown>, enum no borrable

- Importar respaldo y scripts de reparación pueden alterar masivamente producción.
- Respaldo autorizado por correo codificado: frágil ante cambio de propietario.

MEDIOS
- strict=false en backend y muchos any/unknown reducen garantías.
- Permisos/roles se normalizan con variantes en varios archivos; riesgo de divergencia.
- VISTA_DIRECTORIO_BLOQUES aparece en frontend pero no en catálogo backend.
- Conteos de Bloque son derivados y pueden desviarse; existen scripts de auditoría/reconstrucción.
- Transacciones Mongo dependen del tipo de despliegue; algunos fallbacks pierden atomicidad total.
- R2 con fallback local puede ocultar archivos faltantes hasta cambiar de instancia.
- Excel/PDF y agregaciones grandes en cliente pueden consumir memoria.
- Auditoría con snapshots puede almacenar datos personales de más.

BAJOS/DEUDA
- Nombres con mayúsculas inconsistentes y código comprimido en una línea dificultan mantenimiento.
- Documentación existente afirma que loginRoutes autentica, pero la ruta activa es perfilUsuarioRoutes.
- Código comentado y varias bibliotecas UI/tablas sugieren evolución sin limpieza.
- Hay artefactos personales y respaldos junto al repositorio; riesgo de commit accidental.

Errores concretos del chequeo frontend: imports no resueltos de constants/origenAcademico,
constants/tallas, constants/terminosParticipacion, security/permisosCatalogo y types/InscripcionType;
