CORRECCIÓN DEL MÓDULO RESPALDO COMPLETO Y MIGRACIÓN
Fecha: 17 de septiembre de 2026

CAUSA DEL NETWORK ERROR
=======================
El endpoint GET /api/respaldo/exportar cargaba simultáneamente todas las colecciones y todos los
archivos de R2. Cada archivo se convertía a Base64, después se construía un único objeto JSON y se
ejecutaba EJSON.stringify + gzipSync. En producción existían 2.046 objetos. Railway registró dos
respuestas 502 (110.998 ms y 78.527 ms) y Node terminó con:

FATAL ERROR: Reached heap limit Allocation failed - JavaScript heap out of memory

El heap alcanzó aproximadamente 490 MB. Axios recibió una conexión cerrada y solo pudo mostrar
"Network Error". CORS no era la causa: OPTIONS respondía 204.

SOLUCIÓN APLICADA
=================
1. La preparación se ejecuta como trabajo en segundo plano.
2. El frontend inicia el trabajo, consulta el progreso cada dos segundos y descarga al finalizar.
3. MongoDB se exporta colección por colección usando cursor y lotes de 100 documentos.
4. Cada JSON se escribe en un archivo temporal y se incorpora al ZIP progresivamente.
5. Cada objeto de R2 se abre como stream y se incorpora de forma secuencial; no usa Base64.
6. El ZIP final se conserva temporalmente y se devuelve mediante createReadStream con Content-Length.
7. El archivo temporal se elimina después de la descarga o al vencer 30 minutos.
8. Los fallos informan trabajo, etapa, colección/archivo y mensaje real.
9. Restaurar/sincronizar ahora usa almacenamiento temporal de Multer y restaura archivos ZIP por
   stream. El límite del servidor se amplió a 2 GB y el cliente ya no corta cargas/descargas largas
   por timeout. Continúa aceptando los respaldos anteriores .tinkus.gz.
10. "Descargar carpetas visibles" se conserva y genera el mismo ZIP completo, legible y restaurable.
