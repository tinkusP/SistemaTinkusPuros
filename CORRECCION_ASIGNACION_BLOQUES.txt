CORRECCIÓN DEL FLUJO DE ASIGNACIÓN DE BLOQUES
Fecha: 11 de septiembre de 2026

CAUSA RAÍZ
-----------
Producción conservaba el índice MongoDB heredado bloqueId_1_fraternoId_1 con unique=true. Aunque retirar un integrante marcaba su DetalleBloque como INACTIVO, el documento histórico seguía ocupando para siempre el par bloque/fraterno. Al volver a asignarlo al mismo bloque, MongoDB respondía E11000. El catch de asignarFraterno consideraba cualquier E11000 como una carrera de asignación y, al no encontrar una pertenencia activa ganadora, mostraba falsamente “La asignación cambió durante la operación”.

La auditoría de solo lectura confirmó además que no existían asignaciones activas duplicadas, relaciones huérfanas ni perfiles Fraterno duplicados. El problema era el índice heredado, no una doble asignación real del usuario buscado.

CORRECCIÓN
----------
- La definición común vigente continúa siendo: estado distinto de INACTIVO y fechaEliminado=null; el índice de exclusión usa estrictamente estado=ACTIVO y fechaEliminado=null.
- La migración idempotente detecta y sustituye el índice compuesto único bloqueId+fraternoId por el mismo índice no único, apto para consultar y conservar historial.
- Se mantiene fraternoId_activo_1, único y parcial, como protección definitiva contra dos asignaciones activas simultáneas.
- Ya no se ejecutan reparaciones globales de índices dentro del clic de asignación.
- Solo los E11000 atribuibles al índice fraternoId_activo_1 se clasifican como conflicto concurrente.
- Retirar recalcula el contador desde DetalleBloque activos.
- Se agregó movimiento administrativo transaccional entre bloques, con validación de gestión, sexo, cupo por género, cupo total, desactivación del origen, creación del destino y recálculo de ambos contadores.

CONCURRENCIA
------------
El índice único parcial fraternoId_activo_1 es la autoridad final. Dos administradores pueden leer “libre”, pero solo el primer insert ACTIVO gana. El segundo recibe E11000 de ese índice, consulta la asignación ganadora y obtiene un conflicto real con el bloque actual. El movimiento se ejecuta dentro de una transacción MongoDB y no deja simultáneamente origen y destino activos.

DATOS HISTÓRICOS
----------------
Retirar conserva el DetalleBloque original como INACTIVO con fechaRetiro. Reasignar crea un documento ACTIVO nuevo. El índice compuesto deja de ser único para permitir múltiples periodos históricos del mismo par bloque/fraterno.

ÍNDICES
-------
Índice incorrecto observado: bloqueId_1_fraternoId_1, unique=true, sin filtro.
Índice recomendado/aplicado por migración: bloqueId_1_fraternoId_1, unique=false.
Índice de seguridad conservado: fraternoId_activo_1, unique=true, parcial estado=ACTIVO y fechaEliminado=null.
Riesgo: bajo; se relaja únicamente la unicidad histórica redundante, no la unicidad activa.
Rollback: recrear el índice compuesto como único solo sería posible eliminando/consolidando historial repetido, por lo que no se recomienda. El rollback funcional seguro es conservar el índice parcial activo y retirar temporalmente el índice compuesto no único.

FRONTEND
--------
- Después de agregar, retirar o mover se invalidan guias-bloques, buscar-usuarios-bloque-admin, pendientes-bloque y candidato-guia.
- Cada integrante administrativo ofrece “Mover a...” con confirmación y bloques destino activos.
- La interfaz se actualiza sin recargar manualmente la página.

BACKEND
-------
- Búsqueda: GET /api/guias/bloques/buscar-usuarios.
- Agregar existente: POST /api/guias/bloques/integrantes.
- Registrar/agregar: POST /api/guias/bloques/registrar-fraterno.
- Retirar: DELETE /api/guias/bloques/integrantes/:detalleId.
- Mover (nuevo): PATCH /api/guias/bloques/integrantes/:detalleId/mover.
- Todas las rutas administrativas afectadas requieren soloAdministradorReal.

RIESGOS

- El movimiento transaccional requiere MongoDB con soporte de transacciones; producción Atlas lo proporciona.
- El proyecto mantiene controladores extensos preexistentes; no se refactorizaron fuera del flujo afectado.
